## 3. Existing OCR Implementation & Invocation Flow

* **Current Engine:** Google ML Kit Text Recognition (`com.google.mlkit:text-recognition:16.0.0`).
* **Source File:** `app/src/main/java/com/aperture/app/detection/TextRecognitionEngine.kt`
* **Invocation Flow:**
  1. `CameraController` invokes `CameraViewModel.frameAnalyzer` on every incoming CameraX frame.
  2. If `detectionMode == DetectionMode.TEXT_RECOGNITION` and detection is enabled, `TextRecognitionEngine.analyze(imageProxy)` is called.
  3. Frame throttling skips every 3 frames (`skipEveryNFrames = 3`), guarding against congestion using an `AtomicBoolean busy` flag.
  4. An `InputImage.fromMediaImage(mediaImage, rotationDegrees)` is processed with ML Kit's asynchronous `recognizer.process(inputImage)`.
  5. Post-filtering filters out low confidence (< 0.30), short strings (< 2 chars), and extreme bounding box areas (< 0.05% or > 85% of frame).
  6. Results are posted to `CameraViewModel._detectionEvent`, which updates `DetectionOverlay.kt` to draw bounding boxes and text chips on screen.
* *Note:* ML Kit Object Detection (`ObjectDetectionEngine.kt`) is also present in the scaffold for general objects. Both ML Kit engines can be cleanly replaced without modifying the camera lifecycle.

## 4. Image Capture & Image-Processing Flow

* **Current Input Source:** CameraX `ImageAnalysis` provides `ImageProxy` objects in `ImageFormat.YUV_420_888` format.
* **Image Orientation:** Frames from CameraX sensor are typically landscape-oriented and include `imageProxy.imageInfo.rotationDegrees` (usually 90° clockwise on mobile devices in portrait).
* **Current Transformation:** `DetectionOverlay.kt` currently performs post-detection coordinate rotation (`CoordinateMapper`) to map raw sensor coordinates to the `FILL_CENTER` display viewport.
* **For FastALPR Integration:**
  * CameraX 1.3+ includes `imageProxy.toBitmap()`, which converts the `YUV_420_888` buffer directly to an RGB `Bitmap`.
  * Pre-inference rotation via `Matrix().postRotate(rotationDegrees.toFloat())` will ensure upright orientation before letterboxing into the detector.
  * For the on-demand **Analyze** button, the app can either:
    1. Grab the latest frame cached from `ImageAnalysis`, or
    2. Capture directly from `previewView.bitmap` (which provides the exact rendered upright viewport frame).

## 6. Exact Model Input/Output Tensor Requirements

### A. Detector: YOLOv9-tiny 384 End-to-End
* **Input Tensor:**
  * Name: `"images"`
  * Shape: `[1, 3, 384, 384]` (Batch: 1, Channels: 3, Height: 384, Width: 384)
  * Data Type: `float32`
  * Memory Layout: `NCHW`
  * Value Range: Normalized `[0.0f, 1.0f]` (RGB)
* **Output Tensor:**
  * Name: `"output0"`
  * Shape: `[N, 7]` where $N$ is the number of detected candidate boxes.
  * Data Type: `float32`
  * Layout per row: `[batch_index, x1, y1, x2, y2, class_id, score]`
    * `batch_index`: `0`
    * `x1, y1, x2, y2`: Bounding box coordinates in the 384×384 letterboxed canvas space.
    * `class_id`: `0` (license plate)
    * `score`: Detection confidence `[0.0f, 1.0f]`

### B. OCR: CCT-XS v2 Global Plate
* **Input Tensor:**
  * Name: `"input"`
  * Shape: `[1, 64, 128, 3]` (Batch: 1, Height: 64, Width: 128, Channels: 3)
  * Data Type: `uint8` (`0` to `255`, unsigned byte). *The model internally applies normalization.*
  * Memory Layout: `NHWC`
  * Color Order: `RGB`
* **Output Tensors:**
  * **Plate Output:**
    * Name: `"plate"`
    * Shape: `[1, 10, 37]` (10 character slots, 37 alphabet classes)
    * Data Type: `float32`
  * **Region Output (optional):**
    * Name: `"region"`
    * Shape: `[1, 66]` (66 supported country/region classifications)
    * Data Type: `float32`

## 7. Image Preprocessing & OCR Decoding Requirements

To replicate FastALPR Python accuracy on Android:

### 1. Detector Preprocessing (Letterbox 384×384)
* **Formula:**
  $$\text{scale} = \min\left(\frac{384.0}{\text{imgHeight}}, \frac{384.0}{\text{imgWidth}}\right)$$
  $$\text{unpadWidth} = \text{round}(\text{imgWidth} \times \text{scale}), \quad \text{unpadHeight} = \text{round}(\text{imgHeight} \times \text{scale})$$
  $$\text{padLeft} = \frac{384 - \text{unpadWidth}}{2.0}, \quad \text{padTop} = \frac{384 - \text{unpadHeight}}{2.0}$$
* **Image Transform:**
  * Bilinear resize image to $(\text{unpadWidth}, \text{unpadHeight})$.
  * Place onto a 384×384 canvas with solid gray fill color `RGB(114, 114, 114)`.
  * Extract RGB values, divide by $255.0\text{f}$, and write into an `NCHW` `FloatBuffer` of length $1 \times 3 \times 384 \times 384$.

### 2. Detector Postprocessing & Coordinate Recovery
* Discard rows where $\text{score} < 0.25\text{f}$.
* Map coordinates back to original image coordinates:
  $$x_1 = \frac{\text{raw}_{x1} - \text{padLeft}}{\text{scale}}, \quad y_1 = \frac{\text{raw}_{y1} - \text{padTop}}{\text{scale}}$$
  $$x_2 = \frac{\text{raw}_{x2} - \text{padLeft}}{\text{scale}}, \quad y_2 = \frac{\text{raw}_{y2} - \text{padTop}}{\text{scale}}$$
* Clamp $(x_1, y_1, x_2, y_2)$ to the image bounds $[0, \text{imgWidth}]$ and $[0, \text{imgHeight}]$.

### 3. OCR Preprocessing (Direct Resize 128×64)
* Crop the plate bounding box from the upright RGB image.
* Resize cropped bitmap to exactly **$128 \times 64$** (Width = 128, Height = 64) with bilinear interpolation (`keep_aspect_ratio = false`).
* Populate an `NHWC` `ByteBuffer` of size $1 \times 64 \times 128 \times 3 = 24,576\text{ bytes}$ with raw uint8 RGB bytes (`0..255`).

### 4. OCR Output Decoding & Plate Normalization
* **Alphabet (length 37):** `"0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ_"`
* **Pad Character:** `'_'` (at index 36).
* **Decoding Algorithm:**
  1. For each slot $s \in [0..9]$, take index $i = \operatorname{argmax}(\text{logits}[0, s, 0..36])$.
  2. Character $c_s = \text{alphabet}[i]$; slot confidence = $\max(\text{logits}[0, s, 0..36])$.
  3. Form string $S = c_0c_1\dots c_9$, and strip trailing `'_'`.
  4. Clean & normalize according to the existing project rule:
     ```kotlin
     val normalized = rawPlate.replace(Regex("[^A-Z0-9]+"), "").uppercase()
     ```
  5. Validate Tanzanian plate minimum length: $\ge 4$ characters.

* Remove Google ML Kit libraries from `app/build.gradle.kts`:
  * `libs.mlkit.objectdetect`
  * `libs.mlkit.textrecog`
  *(Saves ~10 MB of unused Play Services / ML Kit SDKs).*

### Pure Kotlin / Android Image Handling
* No native OpenCV (`.so`) dependency is required. Android's native `Bitmap`, `Canvas`, and `Matrix` fully support bilinear interpolation, letterbox padding, cropping, and color extraction.

## 10. Potential Technical Blockers & Mitigations

1. **Blocker: Android SDK Location Missing in Terminal**
   * *Finding:* `ANDROID_HOME` is not set by default in the Linux environment; Gradle dry-run failed until `/home/josiamosses/Android/Sdk` was specified.
   * *Mitigation:* Ensure `local.properties` specifies `sdk.dir=/home/josiamosses/Android/Sdk` so `./gradlew` builds consistently both from CLI and IDEs.
2. **Blocker: Camera Orientation Mismatch**
   * *Risk:* If portrait sensor frames are passed unrotated to YOLO, plates will appear 90° sideways, degrading detection and OCR.
   * *Mitigation:* Rotate bitmap by `imageInfo.rotationDegrees` prior to tensor preprocessing.
3. **Blocker: ONNX Asset Loading from APK**
   * *Risk:* ONNX Runtime cannot load paths like `file:///android_asset/...` directly via C++ file descriptors.
   * *Mitigation:* Load model bytes using `context.assets.open(path).readBytes()` and initialize sessions via `OrtEnvironment.createSession(bytes, options)`.
4. **Blocker: Unsigned Byte Handling in Kotlin/Java**
   * *Risk:* Kotlin `Byte` is signed (-128 to 127), whereas CCT OCR expects `uint8`.
   * *Mitigation:* Populate a direct `ByteBuffer` and construct the tensor using `OnnxTensor.createTensor(env, buffer, shape, OnnxJavaType.UINT8)`.
