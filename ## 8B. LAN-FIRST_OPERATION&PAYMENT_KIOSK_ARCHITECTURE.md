## 8B. LAN-FIRST OPERATION AND PAYMENT KIOSK ARCHITECTURE

ZIRP must operate primarily within the site's local network.

The Site Server, Edge Nodes, operator workstations and payment kiosks must communicate through LAN.

Internet connectivity is an additional capability, not a prerequisite for normal local parking operations.

### Local network requirements

- The Site Server must expose the required application services to authorized LAN clients.
- Kiosks must communicate with the Site Server using the local network.
- Edge Nodes must communicate with the Site Server using the local network.
- Local DNS or stable server addressing must be configured.
- Essential application assets must be available locally.
- Loss of internet connectivity must not interrupt local session lookup, tariff calculation, cash collection, local payment recording or payment verification against the local server.
- Monitor LAN connectivity separately from internet connectivity.

### Payment kiosk responsibilities

The kiosk is the physical payment station used by drivers to settle parking fees.

It must support:

- QR receipt scanning.
- Parking-session retrieval over LAN.
- Vehicle image and plate display.
- Entry time and parking duration display.
- Fee calculation from the authoritative tariff configuration.
- Cash payment collection and recording.
- Mobile-money payment initiation when internet connectivity is available.
- Payment status display.
- Receipt printing.
- Payment history lookup according to permissions.

### Cash payment transaction

When cash is collected:

1. Retrieve the correct parking session.
2. Calculate the outstanding amount on the server.
3. Identify the authorized cashier or operator.
4. Record amount received, payment method, session ID, timestamp and receipt reference.
5. Commit the payment transaction to PostgreSQL.
6. Update the session's financial state transactionally.
7. Return confirmation to the kiosk.
8. Make the verified payment available to the exit decision engine.

Do not mark a session paid before the database transaction commits.

Support underpayment, overpayment, cancellation, duplicate submissions, refunds and cash reconciliation according to configured policy.

### Internet failure behaviour

When internet connectivity is lost:

- Local LAN communication must continue.
- Cash payments must continue.
- Local QR lookup must continue.
- Local fee calculation must continue.
- Locally recorded and committed cash payments must be available to exit lanes.
- Mobile-money transactions must remain pending or unavailable until provider verification can be obtained.
- Never assume a payment succeeded because a request timed out.
- Clearly distinguish LAN failure, internet failure and external payment-provider failure.

Implement separate health indicators for Site Server, LAN, internet and payment providers.

## 8C. CACHE STRATEGY AND CONSISTENCY POLICY

Use PostgreSQL as the authoritative source of truth.

Select caching strategies according to the data's consistency and durability requirements.

### No cache for authoritative financial and transaction writes

Do not use disposable cache storage as the only persistence mechanism for:

- Cash payment records.
- Mobile-money payment confirmations.
- Parking session creation.
- Parking session closure.
- Financial ledger entries.
- Exit authorization records.
- Special-access approvals.
- Critical audit events.

These operations must be committed durably before reporting success.

### Cache-aside

Use cache-aside for suitable frequently accessed data:

- Vehicle entitlement reads.
- Tariff configuration.
- Site configuration.
- Gate and camera configuration.
- User permission reads.
- Other frequently accessed reference data.

Define TTL, cache keys, invalidation and stale-data policies.

### Write-through or controlled cache invalidation

For mutable configuration and entitlement data:

1. Commit the authoritative change to PostgreSQL.
2. Invalidate or refresh affected cache entries.
3. Propagate version changes to Edge Nodes.
4. Confirm synchronization or expose synchronization failure.
5. Prevent stale revoked entitlements from authorizing access outside the explicitly approved offline policy.

Use a transactional outbox where necessary to guarantee reliable propagation after database commits.

Do not assume PostgreSQL and Redis updates are one atomic transaction.

### Write-behind

Do not use ordinary Redis write-behind for financial, parking-session or access-control transactions.

For disconnected Edge Nodes, use a durable local event journal rather than disposable cache storage.

The journal must survive process restarts and power failures to the extent supported by the local storage system.

### Cache failure behaviour

The system must define behaviour for:

- Redis unavailable.
- Cache miss.
- Cache corruption.
- Expired cache.
- Stale entitlement snapshot.
- Site Server unavailable.
- Edge Node disconnected.

Critical operations must remain correct when Redis is unavailable.

Do not allow cache failure to produce unauthorized access or financial inconsistency.

## 8D. APPLICATION AND DATABASE PERFORMANCE ENGINEERING

Audit and optimize every relevant subsystem. Do not apply optimizations blindly.

### Duplicate API request prevention

- Identify duplicate concurrent read requests.
- Deduplicate identical in-flight requests where appropriate.
- Debounce search inputs.
- Throttle unnecessary dashboard refreshes.
- Implement backend idempotency for payment and vehicle-event operations.
- Prevent duplicate vehicle events from creating multiple sessions.
- Do not confuse frontend request deduplication with backend transaction protection.

### API pagination

Implement server-side pagination for large collections.

Apply to:

- Parking sessions.
- Payment history.
- Vehicles.
- Audit records.
- Recognition events.
- Reports.
- Users.

Support filtering, sorting and reasonable page-size limits.

Evaluate cursor pagination for rapidly growing event histories.

Do not load entire operational histories into the frontend.

### Static assets and CDN

Determine which assets are public and suitable for CDN delivery.

Use local delivery for essential LAN kiosk and desktop resources.

Do not make parking operations dependent on external CDN availability.

Never publicly expose private vehicle evidence, credentials or sensitive operational data.

### Background processing

Identify slow, non-critical operations and move them to appropriately managed background workers.

Examples:

- Evidence compression and archival.
- Non-critical image uploads.
- Large report generation.
- Notifications.
- Analytics aggregation.
- Log archival.
- Scheduled reconciliation.

Do not defer required durable transaction commits or access decisions to unreliable background jobs.

Use the existing queue infrastructure if suitable. Do not introduce competing queue systems.

### N+1 query elimination

Audit database access in:

- API endpoints.
- Serializers.
- Dashboard queries.
- Reports.
- Vehicle and payment history.
- Operator interfaces.

Use appropriate ORM techniques such as select_related, prefetch_related, annotations and optimized querysets where applicable.

Add query-count tests for important endpoints.

### Dependency optimization

Identify unused, duplicated, vulnerable and unnecessary dependencies.

Verify dynamic imports, SDK loading, packaging and hardware integrations before removal.

Rebuild the Windows application and installer after dependency changes.

### External API timeouts

Every external network request must have:

- Connection timeout.
- Read/response timeout.
- Overall operation deadline.
- Bounded retries.
- Backoff where appropriate.
- Idempotency protection for financial operations.
- Explicit pending and failure states.

Do not retry non-idempotent payment operations blindly.

### Database indexing

Inspect actual SQL queries and execution plans.

Create indexes for frequent plate, session, entitlement, payment and operational lookups.

Evaluate composite and partial indexes where they match actual query patterns.

Measure write overhead and index usefulness.

Avoid unnecessary indexes.

### Connection pooling

Inspect current database connection management.

Implement appropriate connection limits, timeouts, health checks and stale-connection handling.

Evaluate PgBouncer only if the workload and deployment architecture justify it.

Prevent connection exhaustion during simultaneous camera, kiosk and operator activity.

### Frontend rendering

Inspect React components and rendering behaviour.

Prevent unnecessary re-renders caused by:

- Frequently changing camera state.
- Dashboard refreshes.
- WebSocket events.
- Large tables.
- Shared global state.

Use component isolation, appropriate state management, memoization and list virtualization where measurements justify them.

Do not introduce indiscriminate memoization.

### Load balancing and horizontal scaling

First measure central API and database bottlenecks.

Do not introduce multiple central application servers without evidence that a single server is insufficient.

If scaling becomes necessary:

- Keep application instances stateless where possible.
- Put them behind an appropriate reverse proxy/load balancer.
- Share authoritative data through PostgreSQL.
- Use a shared cache only where required.
- Ensure background workers do not execute duplicate jobs.
- Preserve unique ownership of physical cameras and gate controllers.
- Never allow multiple nodes to independently control the same barrier.

Edge Node workload distribution must remain separate from HTTP API load balancing.

## 8E. PERFORMANCE AUDIT AND ACCEPTANCE REPORT

Before optimization, record the baseline.

Measure:

- API p50, p95 and p99 latency.
- Database query count and latency.
- Slowest SQL queries.
- Database connection usage.
- Cache hit and miss rates.
- Queue depth and processing delay.
- Frontend rendering performance.
- CPU and memory consumption.
- Camera frame age and recognition latency.
- LAN communication latency.
- Payment-provider response times.

After optimization, repeat the same tests and produce a before-and-after report.

Demonstrate:

1. Local kiosk operation with internet disconnected.
2. Cash payment recorded and verified through LAN.
3. Mobile-money pending state when provider connectivity is unavailable.
4. Cache failure without financial data loss.
5. Correct cache invalidation after entitlement changes.
6. No duplicate sessions from repeated API requests.
7. Correct pagination of large datasets.
8. No major N+1 query problems in critical endpoints.
9. Bounded database connections.
10. External API timeout and recovery behaviour.
11. No unnecessary frontend rendering under normal updates.
12. Independent operation of multiple camera lanes.
13. Stable operation under the defined traffic and concurrency tests.

Document every optimization, the measured problem it solves, the implementation, test evidence and any remaining limitations.

Do not claim performance improvements without measurements.
